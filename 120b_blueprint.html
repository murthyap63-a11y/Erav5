01 · Architecture

Mixture-of-Experts, not dense — the single biggest lever at this scale

At 120B "total size," the first real fork in the road is dense vs. sparse (MoE). Given your mixture spans code, agentic/tool-use, reasoning, long-context, and multilingual — a genuinely broad capability target — MoE is the right call: it lets you train on far more tokens for the same compute, which matters more for breadth of capability than raw parameter count does.

ComponentRecommendationWhy
Overall shapeMoE, 120B total / ~20B active per token (6× sparsity)~6× cheaper training FLOPs per token than a 120B dense model at equal quality-per-active-param; moderate sparsity (vs. DeepSeek-V3's ~18×) trades some efficiency for a smaller quality gap vs. dense
Experts128 routed experts, top-8 active + 2 always-on shared expertsShared experts (DeepSeek-V3 pattern) capture common cross-domain features so routed experts can specialize more cleanly
Load balancingAuxiliary-loss-free balancing via a learned per-expert bias term, not a large aux-loss coefficientAvoids the classic MoE failure mode where a heavy balancing loss actively fights the main training objective
AttentionGrouped-Query Attention, 48 query heads / 8 KV heads, head dim 128Cuts KV-cache size ~6× vs. full multi-head attention — critical for the long-context targets in your mixture
Positional encodingRoPE, base θ raised during the dedicated long-context stage (Sec. 5), YaRN-style scaling for inference-time extension beyond the trained lengthTrains stably at a moderate context length, then extends further at inference without full retraining
NormalizationRMSNorm, pre-norm, QK-norm on attention logitsQK-norm specifically prevents attention-logit blowups, a common source of loss spikes at this scale
ActivationSwiGLUStandard choice across current open frontier-class models; consistently outperforms ReLU/GeLU variants at scale
Depth × width~80 layers, hidden size 6,144Deeper-and-narrower generally reasons better per-FLOP than shallow-and-wide at this parameter class
Auxiliary objectiveMulti-token prediction (predict token t+2 as well as t+1) via a lightweight extra headMeaningfully improves sample efficiency and downstream coding/reasoning quality per token trained (DeepSeek-V3 finding), can be dropped at inference
Context lengthTrained natively to 128K, extended to ~1M via YaRN + a dedicated long-context stageMatches how current frontier-class models handle long-context — native training up to a point, extension technique beyond it
Vocabulary~230,000 tokens (see Section 4)Sized for the actual mixture — code, math, agentic syntax, and multiple Indic scripts all need dedicated budget, not a shared undersized vocab
MoE's real cost isn't compute, it's communication. Expert parallelism requires all-to-all GPU communication on every forward/backward pass. This is the architecture decision with the biggest hardware/networking implication — see Section 9.

03 · Cleaning pipeline, at scale

Same 10-step pipeline, now distributed

The 10-step pipeline (normalization → language ID → dedup → quality/Gopher/C4 → toxicity → PII → decontamination → code secrets → LaTeX-aware → human audit) built earlier in this conversation applies directly here. At 30T-token scale, two things change:

Distributed execution is mandatory

A single-machine multiprocessing pool (the earlier `--workers` approach) doesn't scale to petabytes. Run the same per-line logic on a distributed framework (Ray or Spark) across a CPU cluster, with the corpus sharded so dedup and language-ID stay correct across shard boundaries.

MinHash/LSH needs a distributed index

A single-process LSH index (as built earlier) can't hold a 30T-token corpus's shingle sets in memory. Use a distributed LSH implementation (or bucket-then-dedup: hash-partition by MinHash band, dedup within each partition, merge) to keep the corpus-wide near-dup guarantee at scale.

Decontamination against a real benchmark suite

Step 7, left empty in earlier test runs, needs to actually run here against the full evaluation suite you'll be measured on: MMLU-Pro, GPQA, HumanEval/SWE-bench, MATH/AIME, BFCL, AgentBench/GAIA, RULER, IndicXTREME/MILU. Skipping this is the single most common way a benchmark score turns out to be memorization, not capability.

04 · Tokenizer

~230,000 tokens — sized for this specific mixture, not a generic default

This follows the same fertility-driven sizing method as the earlier tokenizer design: keep adding vocabulary to a domain until its fertility (tokens/word) stops improving, rather than allocating proportionally to raw corpus share.

DomainTarget fertilityWhy it needs dedicated budget
English / general web1.20×Baseline — largest single content source
Code (15+ languages)1.15×Keywords and common identifiers as single tokens directly improve completion quality and reduce sequence length in repo-scale context
Math / scientific notation1.15×Single-digit tokenization is specifically important for arithmetic reliability; LaTeX commands as whole tokens
Agentic / structural tokensn/a (structural)JSON keys, function-call schema, tool-call delimiters as single tokens — reduces the token overhead of every tool call, which compounds heavily in long agentic sessions
Reasoning-trace formatting1.20×Long chain-of-thought text is mostly natural language, but step-marker/notation tokens benefit from dedicated merges given how much of the token budget reasoning traces consume at inference
Indic languages (pooled, ~18 languages)1.35–1.60×Same rationale as the dedicated India-first design — see the earlier tokenizer report for the full per-language breakdown
Verified by the run report earlier in this conversation — a generic, undersized, single-script-biased vocabulary produced 14.87 tokens/word on real Indic text against a ~1.4× target. That failure mode is exactly what a properly-sized, domain-aware vocabulary here is meant to prevent.
05 · Training curriculum

Five stages, one learning-rate schedule (Warmup–Stable–Decay)

A single flat pretraining run wastes the fact that not all data is equally valuable at every point in training. A staged curriculum lets you control WHEN the model sees what, on top of a WSD (warmup–stable–decay) learning-rate schedule rather than a fixed cosine curve — WSD lets you extend the "stable" phase without redesigning the whole schedule if you decide to train longer.

06 · Compute budget for your mixture

The formula, worked through with real numbers

Training compute (FLOPs)
C ≈ 6 × N_active × D
N_active = active parameters per token (NOT total params for an MoE model) · D = total training tokens

This is the number of tokens (D) you can afford is a function of your compute budget and N_active — for MoE, using active params instead of total params is the whole point: it's why MoE lets you train on dramatically more data for the same FLOPs.

VariantN (used in formula)D (tokens)Total FLOPs
MoE (recommended) — 120B total / 20B active20B30T3.6 × 10²⁴

The MoE payoff in plain terms — for the identical 3.6 × 10²⁴ FLOP budget, a dense 120B model could only train on ~5T tokens instead of 30T. Given a broad seven-domain mixture, more diverse tokens at fixed compute generally beats more parameters at fixed tokens.

07 · Loss correction & optimization

Backprop itself needs no "correction" — training stability at this scale does

Standard backpropagation (reverse-mode autodiff) computes exact gradients; there's no alternative algorithm needed there. What actually needs engineering at 120B-model scale is keeping those gradients well-behaved and recovering cleanly when they aren't:

Optimizer

AdamW as the safe default (β1≈0.9, β2≈0.95, weight decay ~0.1). Muon (a newer matrix-aware optimizer) is worth evaluating on a smaller model first — early results show faster convergence on weight matrices specifically, but it's less battle-tested at 100B+ scale.

LR schedule

Warmup–Stable–Decay (Section 5), not pure cosine — decouples "how long do I train" from "what does my schedule look like," letting you extend the stable phase if more compute becomes available mid-run without redesigning anything.

Gradient clipping

Global-norm clipping (typically to 1.0) on every step — the single cheapest defense against a bad batch producing a destabilizing gradient.

Loss-spike recovery

Monitor gradient norm and loss in real time; on a detected spike, roll back to the last stable checkpoint and skip the offending data shard rather than let training continue on a corrupted trajectory (the "rewind and skip" pattern used in PaLM and OPT training).

Precision

bf16 compute with fp32 master weights and optimizer state (no loss scaling needed, unlike fp16). RMSNorm epsilon and attention logit soft-capping/QK-norm (Section 1) matter here specifically to prevent bf16 overflow in attention.

MoE-specific auxiliary loss

The bias-based load-balancing correction from Section 1 IS a form of "loss correction" in the literal sense — it's a small auxiliary signal that nudges routing without a large competing loss term.

Multi-token prediction loss

The MTP auxiliary head (Section 1) adds a second loss term during pretraining, dropped at inference — improves gradient signal density per token processed.

Distributed correctness

ZeRO-3/FSDP gradient sharding and all-reduce must be bitwise-consistent across ranks — a subtle desync here silently corrupts training without an obvious loss spike, so it's worth its own correctness testing separate from the model architecture.

08 · Agents & tooling infrastructure

Two different meanings of "agent tooling" here — both are needed

Infra to BUILD the model

Distributed data processing (Ray/Spark), training orchestration (Megatron-LM / DeepSpeed / PyTorch FSDP2 on Slurm or Kubernetes), experiment tracking (W&B/MLflow), an automated eval harness (lm-eval-harness-style) running the Section 10 benchmark suite continuously against checkpoints, and fault-tolerant checkpointing given that node failures are routine at this cluster scale.

Tool environments to TEACH agentic capability

This is the part your mixture specifically needs and can't skip: a real sandboxed code-execution environment, a mock/real API-calling layer, a calculator/retrieval tool, and a browsing environment — all wired into both SFT data generation (agentic trajectories kept only if they verifiably complete the task) and RL reward computation (Section 8's verified-reward approach from the earlier blueprint). Unverified synthetic agent data is a known way to actively degrade agentic performance, not improve it.

RL / post-training infra

Fast rollout generation (vLLM or SGLang, not the training framework itself) for RL sampling, a GRPO or PPO trainer, and reward-model or verifier serving at rollout scale. This is a separate, significant infrastructure build from pretraining — budget for it as its own project phase.

Data provenance / lineage

Given the earlier discussion on per-shard provenance manifests (source, license, contributor, content hash) — at this scale, that's not optional bookkeeping, it's what lets you debug a downstream eval regression back to a specific data batch.

10 · Benchmark alignment

What "meeting frontier benchmarks" actually requires beyond this document

Everything above gets you a strong pretrained base model. It does not, by itself, get you to Claude/GPT/Gemini-level benchmark scores — that gap is closed substantially in post-training, which is its own multi-month effort:

Target capabilityEvaluation suite
General reasoningMMLU-Pro, GPQA-Diamond
CodingHumanEval, SWE-bench Verified, LiveCodeBench
MathMATH, AIME, GSM8K
Agentic / tool-useBerkeley Function-Calling Leaderboard, AgentBench, GAIA
Long-contextRULER, needle-in-haystack variants at target length
Indic languagesIndicXTREME, MILU, Aya evaluation suite
Being direct about this — matching frontier-lab benchmark numbers takes large-scale RLHF/RLAIF, extensive human-preference data collection, iterative red-teaming, and many rounds of targeted post-training against exactly these evals — none of which is a pretraining architecture decision. This document is the foundation that post-training effort builds on, not a substitute for it.
